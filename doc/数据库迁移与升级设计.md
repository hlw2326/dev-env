# 数据库迁移与升级设计

**适用：** DevEnv 内部管理数据库（SQLite，`%LOCALAPPDATA%/DevEnv/data/devenv.db`）
**阶段：** 当前为开发阶段，表结构可以随意重构；发布后切换为只增不改（见第十一节）

---

## 一、目标

1. 数据库里有一张迁移记录表，记录每个迁移文件何时安装、是否成功，行为与参考项目 `hlw-mp-admin/php3/database` 的 `migrations` 表一致。
2. 开发阶段允许改任何表、任何字段。改表结构时，代码同步改，不保留旧字段、旧分支、旧写法。
3. 迁移文件与实际库不一致时，启动直接报错，不静默修复，不静默删库。
4. 迁移逻辑集中在 `internal/infra/sqlite/`，业务层不感知。

---

## 二、参考项目的机制与取舍

参考项目（ThinkAdmin + Phinx）的做法：

| 机制 | 说明 |
|------|------|
| 迁移文件 | `database/migrations/{14位时间戳}_{说明}.php`，按版本号升序执行 |
| 记录表 | `migrations`，字段 `version`、`migration_name`、`start_time`、`end_time`、`breakpoint`，主键 `version` |
| 建表与数据分离 | `...0001` 建系统表，`...0002` 写入初始用户、菜单、配置，`...0004` 写入插件菜单 |
| 重复执行 | 已在记录表里的版本不再执行 |
| 建表方式 | `PhinxExtend::upgrade` 对比现有列，缺什么补什么，所以同一份脚本能反复跑 |

本项目的取舍：

| 项 | 决定 | 原因 |
|----|------|------|
| 版本号排序执行、记录表防重复 | 采用 | 核心机制 |
| 建表与初始数据分离到不同文件 | 采用 | 改表结构时不用碰数据脚本 |
| 记录表名 | `system_schema_migrations` | CLAUDE.md 已规定 `system_` 前缀 |
| 记录起止时间 | 采用 `started_at`、`finished_at` | 对应参考项目的 `start_time`、`end_time` |
| `breakpoint` 字段 | 不要 | 本项目没有断点回滚的用法 |
| 增加 `checksum` 字段 | 增加 | 用来发现"已安装的迁移文件又被改了"，参考项目没有这层保护 |
| 按列对比自动补列 | 不做 | 这就是兼容旧结构的做法。本项目直接改建表脚本，库不一致就重建 |
| 版本号格式 | 沿用 `000001` 六位序号 | 与现有文件和 CLAUDE.md 一致，单人开发不需要时间戳防冲突 |

## 三、开发阶段规则

1. **直接改 `000001_init.sql`**。不新增 `ALTER TABLE` 迁移，不写"如果存在旧列则……"。
2. **改表必须同步改全链路代码**，清单见第九节。提交前不允许出现"表已改、代码还在读旧列"的状态。
3. **不写兼容代码**：不保留已废弃的列、不对旧库做探测（`pragma_table_info`、`sqlite_master` 探测）、不在读取时兜底旧格式。
4. **库与脚本不一致时启动报错**，由开发者显式选择重置（见第七节）。重置前自动备份，库里的开发数据不会无声丢失。
5. **建表语句不写 `IF NOT EXISTS`**。迁移只在版本未记录时执行一次，若表已存在说明库被外部改过，应该报错而不是被掩盖。

## 四、迁移文件规范

位置：`internal/infra/sqlite/migrations/`，通过 `go:embed` 打包进程序。

```text
migrations/
├── 000001_init.sql          建全部业务表和索引
└── 000002_seed_settings.sql 初始数据（需要时才建，与建表分离）
```

| 规则 | 说明 |
|------|------|
| 文件名 | `{6位序号}_{snake_case说明}.sql`，序号全局唯一、严格递增，可以不连续 |
| 文件名不合法 | 启动报错，**不跳过**（现有代码是 `continue` 静默跳过） |
| 序号重复 | 启动报错 |
| 事务 | 一个文件一个事务，文件内任一语句失败整体回滚，该版本不入记录表 |
| 职责 | 建表文件只放 DDL；初始数据单独成文件，只放 `INSERT` |
| 编码 | UTF-8，无 BOM，注释用 `--` |
| 外键开关 | 文件里不写 `PRAGMA foreign_keys`，连接层已统一开启，事务内切换该开关无效 |

## 五、迁移记录表

```sql
CREATE TABLE system_schema_migrations (
    version     INTEGER PRIMARY KEY,
    name        TEXT    NOT NULL,
    checksum    TEXT    NOT NULL,
    started_at  TEXT    NOT NULL,
    finished_at TEXT    NOT NULL
);
```

| 字段 | 说明 |
|------|------|
| `version` | 文件名里的序号转成整数，数值排序，不做字符串比较 |
| `name` | 文件名去掉序号和扩展名，如 `init` |
| `checksum` | 文件内容的 SHA-256 十六进制，换行统一成 `\n` 后再算，避免 Git 换行转换造成误报 |
| `started_at` / `finished_at` | UTC，RFC 3339 |

与 CLAUDE.md 第 2 条的差异：版本号由 TEXT 改为 INTEGER，新增 `checksum`，`applied_at` 拆成起止两个时间。文档与 CLAUDE.md 需要同步修改（见第十节）。

这张表**不放进迁移文件**。它是迁移程序自己的状态，由 Go 代码在执行迁移之前创建，其余业务表才由迁移文件创建。

## 六、启动流程

`sqlite.Open(path, opts)` 内部：

```
1. 创建数据目录，打开连接（外键、WAL、busy_timeout 的 pragma 沿用现有写法）
2. 创建 system_schema_migrations（如不存在）
3. 读取并校验内嵌迁移文件：文件名格式、序号唯一
4. 读取已记录的迁移，与文件逐项核对：
     记录里有、文件里没有        → 漂移（文件被删）
     记录与文件的 checksum 不同  → 漂移（文件被改）
     文件序号 < 已记录的最大序号且未记录 → 漂移（中间插了旧序号）
5. 有漂移：
     opts.ResetOnDrift = false → 返回 SchemaDriftError，列出每一项差异，启动终止
     opts.ResetOnDrift = true  → 备份、删库、回到第 1 步重建
6. 无漂移，有待执行迁移：
     库非空 → 先备份（reason=pre-migrate）
     按序号升序逐个执行，每个文件一个事务，事务内完成"执行 SQL + 写记录"
7. 全部完成后执行 PRAGMA foreign_key_check，有结果即报错
8. 返回 *DB
```

失败原则：任何一步失败都返回错误，不吞错、不继续启动。`app.go` 目前对 `Bootstrap` 失败直接 `panic`，用户看到的是崩溃。建议改为弹出 Wails 对话框展示错误文本后退出，错误里带上漂移明细和重置方法。

## 七、漂移处理与重置

### 7.1 重置开关

开发者在启动前设置环境变量 `DEVENV_DB_RESET=1`，由 `internal/app/bootstrap.go` 读取并通过 `Options.ResetOnDrift` 传给 `sqlite.Open`。`sqlite` 包本身不读环境变量。

只有出现漂移时才会重置。库与脚本一致时设了该变量也不动库，避免每次启动都清库。

### 7.2 重置动作

1. 以 `VACUUM INTO` 备份到 `backups/`，WAL 模式下直接复制文件不安全。
2. 关闭连接。
3. 删除 `devenv.db`、`devenv.db-wal`、`devenv.db-shm`。
4. 重新打开并执行全部迁移。

备份成功是重置的前提，备份失败则中止并报错。

### 7.3 为什么默认不自动重置

开发库里可能有已经配好的站点、已登记的运行环境。每次改一行 SQL 就自动清库会让人养成"反正会丢"的习惯，一次误触发就是真丢数据。多一个环境变量的成本很低，所以默认不自动。

目录：`%LOCALAPPDATA%/DevEnv/data/backups/`

| 项 | 规则 |
|----|------|

## 十一、发布阶段切换

进入发布阶段后规则反过来：

1. **已发布的迁移文件冻结**。内容不得再改，`checksum` 校验即是保护：改了就会报漂移，而且发布版不提供重置开关。
2. **所有结构变更只能新增迁移文件**，例如 `000003_add_service_auto_restart.sql`。
3. **不写回滚迁移**。要撤销一次变更，就再新增一个迁移做反向变更。
4. **删列、改列走 SQLite 的重建流程**：建新表、拷数据、删旧表、改名，写在一个迁移文件里。
5. 在测试里固化"已发布迁移的 checksum 清单"，防止有人在发布后手滑改了旧文件。

切换时机由你决定，切换那天要做三件事：确定最终的 `000001_init.sql`，生成 checksum 清单，关闭或移除 `DEVENV_DB_RESET`。

## 十二、测试

迁移执行器接收 `fs.FS` 而不是直接读全局 `embed.FS`，这样测试可以用 `testing/fstest.MapFS` 构造任意迁移集合，不用造真实文件。

| 用例 | 预期 |
|------|------|
| 空库首次打开 | 全部迁移执行，记录表条数等于文件数，`finished_at` 非空 |
| 同一个库再次打开 | 不重复执行，记录表不变 |
| 追加一个更大序号的迁移 | 只执行新增的一个，并先产生一份 `pre-migrate` 备份 |
| 修改已记录迁移的内容 | 返回 `SchemaDriftError`，库未被改动 |
| 删除已记录的迁移文件 | 同上 |
| 新增一个序号小于已记录最大值的迁移 | 同上 |
| 漂移且 `ResetOnDrift=true` | 生成 `pre-reset` 备份，库被重建，记录表与新文件一致 |
| 无漂移且 `ResetOnDrift=true` | 库原样保留，不备份 |
| 迁移文件中间一条语句出错 | 整个文件回滚，记录表没有该版本，业务表也没有半成品 |
| 文件名不合规、序号重复 | 返回错误 |
| 外键校验 | 构造一个会产生孤儿行的迁移，打开时返回错误 |
| 备份保留 | 连续产生 7 份，目录里只剩最新 5 份 |

现有的 `repo_test.go` 和 `site_test.go` 通过 `sqlite.Open(dbPath)` 建库，签名改后需要同步（`Open(dbPath, sqlite.Options{})`）。
