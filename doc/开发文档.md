# 项目目录规范与 Go 后端模块接口规范

**项目名称：** DevEnv  
**文档版本：** V1.0  
**适用技术：** Go + Wails + Vue 3 + TypeScript + SQLite  
**目标平台：** Windows 10 / Windows 11 64 位  
**文档用途：** 项目开发标准、模块边界约束、AI 编程规范

---

# 第一部分：项目目录规范

## 一、总体设计原则

### 1.1 核心原则

1. **按业务模块组织代码**：PHP、项目、数据库、Web 服务器分别维护自己的业务逻辑。
2. **UI 与业务逻辑分离**：Vue 负责交互，Go 负责系统操作和业务处理。
3. **Wails 只作为通信边界**：前端不直接操作操作系统进程、文件系统或数据库。
4. **依赖方向清晰**：业务模块不应相互随意引用内部实现。
5. **接口优先，避免过度抽象**：只在确实需要解耦、替换实现或模拟测试的地方定义接口。
6. **数据和程序分离**：应用升级不能无故覆盖用户项目、数据库文件或运行环境。
7. **模块可独立测试**：核心业务逻辑尽量不依赖 Wails 窗口或 Vue 页面。
8. **禁止随意创建目录**：新增模块必须有明确的业务职责，并遵守本规范。

### 1.2 统一架构

整个应用划分为五层：

| 层级 | 职责 | 主要目录 |
|---|---|---|
| 桌面入口层 | 应用启动、窗口及生命周期 | `main.go`、`app.go` |
| 接口适配层 | Wails 方法、DTO 转换、事件通知 | `internal/transport/wails/` |
| 应用服务层 | 用例编排、权限校验、业务流程 | `internal/app/` |
| 领域业务层 | 项目、PHP、服务等业务规则 | `internal/domain/` |
| 基础设施层 | 文件、进程、SQLite、下载等实现 | `internal/infra/` |

基本调用方向：

```text
Vue 3 + TypeScript
        │
        ▼
Wails 绑定方法
        │
        ▼
Transport / Wails
        │
        ▼
Application Services
        │
        ├── Domain
        │
        └── Ports / Interfaces
                 │
                 ▼
             Infrastructure
                 │
        ┌────────┼────────┐
        ▼        ▼        ▼
      文件系统   进程管理   SQLite
```

**重要约束：** 基础设施层不能反向依赖应用服务层，业务领域层也不能依赖 Wails、Vue 或具体的数据库实现。

### 2.1 目录使用规则

- `main.go`：只负责创建应用实例和启动 Wails。
- `app.go`：负责桌面应用生命周期，例如启动、关闭和必要的初始化调用。
- `internal/app/`：处理完整的业务用例，例如安装 PHP、创建项目、启动服务。
- `internal/domain/`：保存业务模型、业务规则和领域错误。
- `internal/ports/`：声明业务需要的外部能力。
- `internal/infra/`：提供接口的实际实现。
- `internal/transport/wails/`：把 Wails 前端请求转换成应用服务调用。
- `frontend/src/api/`：封装前端调用的 Go 绑定方法。
- `frontend/src/types/`：前端自行维护的业务类型，或存放生成的绑定类型。
- `docs/`：保存正式设计规范，不能成为随意堆放临时笔记的目录。

### 2.2 目录结构的实施原则

上述是目标结构，不要求第一次提交就创建所有空目录。

应按照开发顺序逐步建立实际使用的模块。不要因为架构图中出现了某个目录，就立即创建大量没有用途的文件。

## 三、Go 文件命名规范

### 3.1 文件名

统一使用小写字母和下划线。

推荐：

```text
php_service.go
project_service.go
process_manager.go
sqlite_repository.go
windows_process.go
```

不推荐：

```text
PhpService.go
ProjectService.go
ProcessManager.go
```

测试文件统一使用 `_test.go`：

```text
php_service_test.go
project_service_test.go
process_manager_test.go
```

### 3.2 包命名

包名使用简短、小写、单数形式。

推荐：

```go
package php
package project
package process
package filesystem
```

不推荐：

```go
package phpService
package projects
package commonUtils
```

避免创建含义模糊的 `common`、`manager`、`helper`、`utils` 大杂烩包。只有职责明确且被多个模块真正复用的代码才应抽取公共包。

### 3.3 类型与方法命名

```go
type PHPVersion struct{}

type ProjectService struct{}

func (s *ProjectService) CreateProject() {}

func (s *ProjectService) GetProject() {}
```

导出标识符使用 `PascalCase`，私有标识符使用 `camelCase`。

Go 的缩写按惯例书写，例如 `ID`、`URL`、`HTTP`、`JSON`。前端 TypeScript 则统一使用 `camelCase`，与 Go 的绑定规则保持一致。

# 第二部分：Go 后端模块接口规范

## 四、模块职责与边界

### 4.1 应用入口模块

文件：

```text
main.go
app.go
internal/app/bootstrap.go
```

职责：

- 创建应用实例。
- 加载配置。
- 初始化 SQLite。
- 初始化基础设施。
- 组装应用服务。
- 注册 Wails 绑定对象。
- 管理启动和退出流程。

禁止：

- 在 `main.go` 中编写 PHP 安装逻辑。
- 在 `app.go` 中直接拼接大量 Nginx 配置。
- 把全部业务方法堆到一个巨大 App 结构体中。

### 4.2 PHP 模块

目录：

```text
internal/domain/php/
internal/app/php_service.go
internal/transport/wails/php.go
```

职责：

- 枚举本地 PHP 版本。
- 注册和移除版本。
- 获取版本信息。
- 检查 PHP 可执行文件。
- 解析 PHP 扩展信息。
- 读取和修改 `php.ini`。
- 设置默认 CLI 版本。
- 为项目提供 PHP 版本绑定信息。

PHP 模块不能直接负责：

- 创建完整的项目业务记录。
- 管理所有数据库服务。
- 修改其他模块的数据库表。
- 在 Vue 页面中维护 PHP 业务规则。

### 4.3 项目模块

职责：

- 创建项目记录。
- 导入已有目录。
- 验证项目路径。
- 保存项目与 PHP 版本的关联。
- 查询项目列表。
- 更新项目配置。
- 删除项目管理记录。

删除项目记录与删除项目文件必须分开处理。默认删除记录不能直接递归删除用户目录。

### 4.4 Web 服务器模块

职责：

- 管理 Nginx 等 Web 服务器版本。
- 生成站点配置。
- 验证配置。
- 启动、停止和重启服务器。
- 查询进程状态。
- 检查端口占用。

Web 服务器模块不应自行修改项目数据库中的业务记录，应通过项目应用服务或相应的业务接口读取必要信息。

### 4.5 数据库模块

职责：

- 管理 MySQL、PostgreSQL 等外部数据库实例。
- 管理实例配置。
- 初始化实例。
- 启动和停止数据库服务。
- 备份与恢复。
- 查询数据库进程状态。

注意区分两类数据库：

1. **应用内部 SQLite**：保存 DevEnv 自己的项目、配置和服务元数据。
2. **用户数据库服务**：供 PHP 项目使用的 MySQL、PostgreSQL 等。

二者必须使用不同的数据目录和连接配置，不能混为一谈。

### 4.6 进程管理模块

职责：

- 启动外部程序。
- 保存运行中的进程句柄。
- 记录 PID 和启动参数。
- 停止进程。
- 监控退出状态。
- 发送运行状态事件。
- 处理异常退出。

进程模块只负责通用进程生命周期，不应在里面实现 PHP 版本切换、项目创建等业务。

### 4.7 下载与安装模块

职责：

- 下载官方发布的运行环境。
- 处理下载进度。
- 校验文件完整性。
- 解压到指定目录。
- 管理临时文件。
- 取消下载或安装任务。
- 处理失败后的清理与恢复。

下载器不应自行决定某个 PHP 版本是否允许安装。版本合法性、安装目标和业务规则由应用服务层决定。

## 五、接口设计原则

### 5.1 接口由使用方定义

Go 接口应尽量定义在需要该能力的模块附近，而不是为了“统一管理”把所有接口集中到一个巨大文件中。

例如，进程管理接口由应用服务需要的能力决定：

```go
package ports

import "context"

type ProcessSpec struct {
    Executable  string
    Args        []string
    WorkingDir  string
    Environment []string
}

type ProcessInfo struct {
    PID     int
    Running bool
}

type ProcessManager interface {
    Start(
        ctx context.Context,
        spec ProcessSpec,
    ) (ProcessInfo, error)

    Stop(
        ctx context.Context,
        pid int,
    ) error

    GetStatus(
        ctx context.Context,
        pid int,
    ) (ProcessInfo, error)
}
```

这只是基础接口示例。实际实现还应考虑 Windows 进程句柄、标准输出、标准错误、优雅退出和子进程生命周期。

### 5.2 不创建无意义的接口

如果某个结构只有一种实现，也没有测试替换、依赖解耦或未来扩展的实际需求，可以直接使用具体类型。

不要为每一个结构都创建：

```text
IProjectService
ProjectServiceInterface
ProjectServiceImpl
```

这类命名并不是 Go 的推荐惯例，也容易产生不必要的抽象层。

### 5.3 不跨层传递数据库模型

数据库记录、领域模型、Wails DTO 是三种不同用途的数据结构。

- 数据库模型：负责持久化。
- 领域模型：负责业务规则。
- DTO：负责前后端通信。

简单模块可以复用部分结构，但不能因为方便，就把 SQLite 查询结果直接作为整个应用的公开 API。

## 六、统一数据结构规范

### 6.1 项目领域模型

文件：`internal/domain/project/model.go`

```go
package project

import "time"

type Project struct {
    ID            string
    Name          string
    Path          string
    PHPVersionID  string
    CreatedAt     time.Time
    UpdatedAt     time.Time
}

type CreateInput struct {
    Name         string
    Path         string
    PHPVersionID string
}

type UpdateInput struct {
    ID           string
    Name         string
    PHPVersionID string
}
```

领域模型不应直接引用 Wails 生成的前端绑定类型。

### 6.2 前端 DTO

文件：`internal/transport/wails/dto/project.go`

```go
package dto

type ProjectDTO struct {
    ID           string `json:"id"`
    Name         string `json:"name"`
    Path         string `json:"path"`
    PHPVersionID string `json:"phpVersionId"`
    CreatedAt    string `json:"createdAt"`
    UpdatedAt    string `json:"updatedAt"`
}
```

这里的 `json` 标签用于定义数据序列化时的字段名。具体前端绑定方法的实际序列化行为仍应以项目采用的 Wails 版本为准。

### 6.3 时间格式

前后端通信中的时间统一使用 ISO 8601 / RFC 3339 格式，例如：

```text
2026-10-14T10:30:00+08:00
```

数据库内部可根据选定的 SQLite 驱动使用统一的时间存储策略。

## 七、应用服务接口规范

应用服务是前端调用业务的主要入口。每个服务负责一个清晰的业务领域。

### 7.1 项目服务

文件：`internal/app/project_service.go`

```go
package app

import (
    "context"

    "devenv/internal/domain/project"
)

type ProjectRepository interface {
    Create(
        ctx context.Context,
        item project.Project,
    ) error

    GetByID(
        ctx context.Context,
        id string,
    ) (project.Project, error)

    List(
        ctx context.Context,
    ) ([]project.Project, error)

    Update(
        ctx context.Context,
        item project.Project,
    ) error

    Delete(
        ctx context.Context,
        id string,
    ) error
}

type ProjectService struct {
    repo ProjectRepository
}

func NewProjectService(
    repo ProjectRepository,
) *ProjectService {
    return &ProjectService{
        repo: repo,
    }
}
```

上述示例展示接口和构造方式。生产代码应进一步定义输入验证、领域错误、事务边界和完整业务方法。

### 7.2 PHP 服务

建议对外提供以下应用能力：

```text
ListVersions
GetVersion
RegisterVersion
RemoveVersion
SetDefaultVersion
GetExtensions
GetConfiguration
UpdateConfiguration
```

注意：`RemoveVersion` 必须检查是否有项目正在引用该版本；如果存在依赖，应拒绝删除或要求用户先解除关联。

### 7.3 运行环境服务

建议对外提供：

```text
ListRuntimes
InstallRuntime
UninstallRuntime
GetRuntimeStatus
GetInstallProgress
CancelInstall
```

安装和卸载需要支持任务状态查询。不要要求前端通过长时间等待一个同步方法来完成整个下载与安装流程。

### 7.4 Web 服务器服务

```text
GetStatus
Start
Stop
Restart
ValidateConfig
ReloadConfig
GetLogs
```

`ValidateConfig` 应先检查配置文件语法；`Restart` 应处理启动失败和原有服务仍在运行的情况。

### 7.5 数据库服务

```text
ListInstances
CreateInstance
GetInstance
UpdateInstance
StartInstance
StopInstance
BackupInstance
RestoreInstance
GetStatus
```

数据库备份与恢复需要独立的任务状态、目标路径检查和错误恢复机制。

## 八、Wails 通信接口规范

### 8.1 绑定层职责

Wails 绑定对象只负责：

1. 接收前端参数。
2. 进行基础参数校验。
3. 调用应用服务。
4. 转换返回 DTO。
5. 返回明确的错误信息。
6. 在需要时向前端发送事件。

禁止直接在绑定层执行复杂 SQL、安装 PHP、操作大量文件或实现完整的业务流程。

### 8.2 示例：项目绑定

文件：`internal/transport/wails/projects.go`

```go
package wails

import (
    "context"

    "devenv/internal/app"
    "devenv/internal/transport/wails/dto"
)

type ProjectsAPI struct {
    service *app.ProjectService
}

func NewProjectsAPI(
    service *app.ProjectService,
) *ProjectsAPI {
    return &ProjectsAPI{
        service: service,
    }
}

func (a *ProjectsAPI) ListProjects() (
    []dto.ProjectDTO,
    error,
) {
    // 调用应用服务。
    // 将领域模型转换为 DTO。
    // 生产实现还需要正确传递请求上下文。
    return nil, nil
}

var _ = context.Background
```

这是接口骨架，不是可以直接投入使用的完整实现。正式实现应删除示例中的占位返回，采用实际业务逻辑。

### 8.3 上下文传递

涉及下载、进程、文件操作或数据库查询的方法，应在内部业务接口中传递 `context.Context`，以便支持取消、超时和退出控制。

Wails 绑定层不应凭空假设存在一个可直接传入的前端 `context.Context`。应根据所使用的 Wails 版本，从其生命周期回调或上下文管理机制中获取应用上下文，再传递给应用服务。

### 8.4 前端 API 封装

前端应将 Go 绑定调用统一封装在 `frontend/src/api/` 中。

例如：

```ts
// frontend/src/api/projects.ts

import {
  ListProjects,
} from '../../wailsjs/go/transport/wails/ProjectsAPI'

export async function listProjects() {
  return await ListProjects()
}
```

以上导入路径仅用于说明封装方式。实际路径、生成的包名和方法名应以 Wails 项目初始化后生成的绑定文件为准。

Vue 页面不得在多个地方重复编写相同的底层绑定调用。

## 九、错误处理规范

### 9.1 错误分类

至少区分以下错误类别：

| 类别 | 示例 |
|---|---|
| 参数错误 | 项目名称为空 |
| 业务冲突 | PHP 版本仍被项目引用 |
| 资源冲突 | 端口已被占用 |
| 权限错误 | 无权修改 hosts 文件 |
| 外部程序错误 | Nginx 启动失败 |
| 文件系统错误 | 安装目录无法写入 |
| 数据持久化错误 | SQLite 写入失败 |
| 取消或超时 | 下载任务被取消 |

### 9.2 统一错误原则

- 使用 `fmt.Errorf("...: %w", err)` 保留底层错误链。
- 不要忽略关键错误。
- 不要把底层错误原文直接作为唯一的用户提示。
- 不要在每一层重复记录同一错误，避免日志重复。
- 公开给前端的错误不得包含数据库密码、令牌或其他敏感信息。

可以在绑定层将内部错误转换成稳定的错误代码，例如：

```text
PROJECT_PATH_INVALID
PHP_VERSION_IN_USE
PORT_ALREADY_IN_USE
PERMISSION_DENIED
PROCESS_START_FAILED
```

前端根据错误代码展示本地化提示，而不是依赖匹配错误字符串。

## 十、进程生命周期与并发规范

### 10.1 统一管理外部进程

所有 PHP、Nginx、MySQL、PostgreSQL 等外部服务，都必须通过统一的进程管理设施启动和监控。

禁止不同业务模块自行随意创建不受管理的长期子进程。

### 10.2 服务状态

建议至少定义：

```text
stopped
starting
running
stopping
failed
```

状态应来自进程信息和必要的健康检查，不能只根据用户点击了启动按钮就认定服务已运行。

### 10.3 重复操作

必须处理：

- 重复启动。
- 重复停止。
- 启动过程中再次点击启动。
- 服务异常退出。
- 应用关闭时仍有子进程运行。
- 端口被其他程序占用。

同一个服务实例的启动、停止和重启操作需要串行化，避免并发操作破坏状态。

### 10.4 退出策略

应用关闭时，应根据用户设置和服务类型采取明确策略：

- 保持服务继续运行。
- 先尝试正常停止服务。
- 超时后提示用户或执行受控的强制结束。

不能默认认为关闭桌面窗口就会自动、正确地结束全部外部服务。

## 十一、数据库访问规范

### 11.1 Repository 职责

Repository 只负责数据持久化，例如：

```text
Create
GetByID
List
Update
Delete
```

复杂业务规则放在应用服务或领域服务中，不应将整个业务流程写进 SQL 查询方法。

### 11.2 SQLite 规范

- 统一初始化数据库连接。
- 使用迁移脚本管理结构变化。
- 使用参数化查询。
- 对相关的多步写操作使用事务。
- 明确外键约束策略。
- 为经常查询的字段添加必要索引。
- 备份时考虑 SQLite WAL 等文件状态，避免直接复制活动数据库文件而造成不一致。
- 升级失败时保留原数据库备份。

### 11.3 迁移规范

每次数据库结构变更必须有版本记录。

迁移脚本应可追踪，禁止应用每次启动时无条件重建数据表，也禁止在没有备份或恢复策略的情况下直接删除旧字段。

## 十二、测试规范

### 12.1 单元测试

优先测试：

- 路径校验。
- PHP 版本解析。
- 项目业务规则。
- 版本依赖检查。
- 端口冲突处理。
- 服务状态转换。
- 配置生成逻辑。

### 12.2 集成测试

测试：

- SQLite Repository。
- 项目创建和查询。
- 运行环境注册。
- 服务启动和停止。
- 配置验证。
- 安装失败后的清理。

### 12.3 Windows 专项测试

必须覆盖：

- 路径包含空格。
- 中文目录名。
- 用户目录权限。
- 管理员权限差异。
- 端口占用。
- 进程异常退出。
- 应用强制关闭。
- 杀毒软件或系统策略阻止执行。

### 12.4 测试隔离

测试不能直接修改真实用户项目目录，也不能操作开发者当前正在使用的数据库。

应通过临时目录、测试数据库和可替换的进程管理实现来隔离测试环境。

# 第三部分：AI 编程约束

## 十三、Claude Code 开发规则

建议在项目根目录创建 `CLAUDE.md`，将以下规则作为开发时的强制约束。

### 13.1 架构约束

1. 新增代码前，先检查现有目录和模块，禁止重复创建同一职责的服务。
2. 严格遵守 `internal/app/`、`internal/domain/`、`internal/ports/`、`internal/infra/` 和 `internal/transport/wails/` 的职责边界。
3. 业务逻辑不得写在 Vue 页面中。
4. Wails 绑定层不得直接实现复杂业务。
5. 领域模型不得依赖 Wails 和 SQLite 驱动。
6. 不允许通过循环依赖解决模块调用问题。
7. 不得随意创建 `common`、`helpers` 等通用大杂烩模块。
8. 新增公共接口时，必须说明实际解耦需求和调用方。

### 13.2 编码约束

1. 所有 Go 代码必须通过 `gofmt`。
2. 所有新增业务逻辑必须有对应测试。
3. 所有错误必须显式处理或有充分理由地传播。
4. 禁止使用 Shell 字符串拼接执行包含用户输入的命令。
5. 所有用户输入的路径必须经过校验。
6. 不得把敏感信息写入日志。
7. 不得为了完成单一需求大规模重构无关代码。
8. 不得引入未经确认的大型依赖。
9. 修改公开接口时，必须同步修改调用方、绑定文件和测试。
10. 不得在业务模块中直接修改其他模块的内部数据库结构。

### 13.3 交付约束

每次完成开发任务后，必须说明：

- 修改了哪些文件。
- 新增了哪些接口。
- 哪些模块受到影响。
- 执行了哪些测试。
- 是否存在未完成的部分。
- 是否涉及数据库迁移或用户数据风险。

没有实际执行测试时，不得声称测试通过。

## 十五、最终约定

本项目统一遵守以下架构规则：

- Go 负责系统能力和后端业务。
- Vue 3 + TypeScript 负责用户界面。
- Wails 负责桌面通信和应用生命周期。
- SQLite 负责应用自身的管理数据。
- PHP、Nginx、MySQL、PostgreSQL 等服务由独立进程运行。
- `internal/app/` 是业务用例的主要入口。
- `internal/transport/wails/` 是前后端通信边界。
- `internal/infra/` 是外部资源和系统能力的实现层。
- 所有公开接口应具有清晰的数据结构、错误处理和测试策略。
- 所有数据迁移、文件删除、环境卸载和进程结束操作都必须考虑失败恢复。

**本规范的最终目标不是目录越多越好，而是确保项目在持续增加 PHP、数据库、虚拟主机、下载、更新和诊断功能后，依然能够清晰维护、独立测试和安全迭代。**
